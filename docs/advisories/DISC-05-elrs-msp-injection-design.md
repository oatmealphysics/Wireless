# DISC-05: ELRS v3 + Betaflight — Unauthenticated MSP Command Injection via OTA

**Advisory type:** Sanitized design advisory (no operational payload)
**Date:** 2026-10-26
**Status:** Draft — pending maintainer contact

## Summary

ExpressLRS OTA v3, as integrated in Betaflight 4.4.2's SPI ELRS receiver,
provides no authentication or encryption layer beyond CRC-14 validation,
FHSS channel alignment, and model match. An attacker who recovers the
target's 6-byte UID (partially broadcast in every SYNC packet) can forge
CRC-valid packets and inject arbitrary MSP commands through the
MSP-over-ELRS path. The full Betaflight MSP command table is accessible
once the attacker achieves ELRS connection state.

This is an **inherent design property** of ELRS v3 (no encryption, CRC-only
integrity, UID-seeded everything). The specific safety-critical impact
arises from the combination of this design with Betaflight's MSP handler,
which permits several dangerous commands without an ARMED check.

## Affected components

- **ExpressLRS OTA v3** (the air protocol design)
- **Betaflight 4.4.2** SPI ELRS receiver integration
- Likely other Betaflight versions with SPI ELRS and MSP-over-ELRS compiled in

## Design-level findings

### 1. No authentication beyond CRC

The ELRS v3 CRC14 initializer is static for the session:
`(UID[4] << 8 | UID[5]) ^ 3`. Since UID[4] and UID[5] are broadcast in every
SYNC packet, the CRC initializer is derivable from a single passive capture.
There is no per-packet nonce in the CRC computation (v4 adds nonce XOR).

### 2. FHSS sequence is deterministic from UID

The 240-entry hop table is generated by a standard LCG seeded from
`UID[2:5] ^ OTA_VERSION_ID`. Given the UID, the complete hop sequence is
known.

### 3. Model match is effectively disabled

When `model_id = 255` (0xFF), the model XOR is zero, and model match always
succeeds. This is the default/common configuration.

### 4. MSP-over-ELRS reaches the full command table

Once an attacker achieves `ELRS_CONNECTED` state with a valid CRC and model
match, MSP packets are dispatched through `processRFMspPacket()` to the
standard Betaflight MSP handler. The runtime `feature -TELEMETRY` setting
does NOT gate MSP receipt in 4.4.2.

### 5. Safety-critical commands lack ARMED checks

The following MSP commands execute without checking ARMING_FLAG(ARMED):

| Command | Effect | MSP payload size |
|---|---|---|
| MSP_SET_ARMING_DISABLED | **Force disarm in flight** (immediate motor shutdown) | 2 bytes |
| MSP_REBOOT | **Reboot FC** (loss of motor control; DFU mode option) | 1 byte |
| MSP_SET_MOTOR | Write motor values (effective when disarmed) | 8 bytes |
| MSP_SET_FAILSAFE_CONFIG | Rewrite failsafe parameters (delay, procedure) | 8 bytes |
| MSP_SET_RAW_GPS | Overwrite GPS solution (poison GPS Rescue) | 14 bytes |
| MSP_SET_RX_CONFIG | Overwrite ELRS UID (lock out real TX) | Variable |
| MSP_SET_PID / PID_ADVANCED | Destabilize flight (zero gains, extreme D) | Variable |
| MSP_SET_BOARD_ALIGNMENT | Flip orientation reference (180° roll) | 6 bytes |

### Attack chain summary

```
Passive SYNC capture → UID[4:5] + partial UID
  → Rainbow table or FHSS seed recovery → full UID
  → CRC14 init + FHSS sequence + model match
  → Forge CRC-valid ELRS packets on correct hop channel
  → Achieve ELRS_CONNECTED state
  → Inject MSP_SET_ARMING_DISABLED → force disarm in flight
```

## Note on scope

This finding describes the security model of a well-known open-source
protocol. The ELRS project is aware that v3 has no encryption. The specific
contribution of this advisory is:

1. The detailed MSP command surface accessible after pairing
2. The safety-critical commands that execute without ARMED checks
3. The confirmation that MSP remains reachable even with runtime telemetry
   disabled
4. The failsafe suppression interaction (see DISC-04)

This may be more appropriate as an **informational security assessment** sent
to both Betaflight and ExpressLRS maintainers rather than a traditional
vulnerability report.

## Remediation considerations

**For ELRS:** OTA v4 adds nonce XOR to the CRC, raising the per-packet
forgery bar. Encryption (when available) would address the fundamental
design gap. Neither is available for v3 targets.

**For Betaflight:**
- Add ARMED checks to safety-critical MSP commands (SET_ARMING_DISABLED,
  REBOOT, SET_FAILSAFE_CONFIG, SET_RAW_GPS, SET_BOARD_ALIGNMENT, SET_PID).
- Consider a separate MSP permission level for OTA-delivered commands
  vs. serial/USB commands.
- Consider rate-limiting or source-validating MSP-over-ELRS.
